**規約の正本は [CLAUDE.md](../CLAUDE.md) です。ここには規約を書きません。** ここに書くのは、各決定の要旨と根拠（数値があれば数値）、そして今の規約がどこにあるかだけです。書いてあることが CLAUDE.md やコードと食い違ったときは、CLAUDE.md とコードが正しいものとして読んでください。

## 読み方

- 番号は「AD-<通し番号>」です。AD-7 と AD-14 のように、下位の番号（AD-7a、AD-14.4 など）を持つ決定があります。AD-11 の較正の項目は U1、選択肢が変わるウィジェットの項目は R-10、CV で `fit` の上書きが通らないことの項目は R1 です。
- 1 項目は「決めたこと（1〜3 行）」「根拠」「今の規約の場所」の順です。あとから訂正や撤回があったものは、訂正後の内容を書き、末尾に「訂正:」の 1 行を付けています。
- 見出しは `### <番号> <題名>` の形で、番号を先頭に置いています（この形を、参照の漏れを調べるテストが読みます）。
- 「（参照なし）」と付いた項目は、いまコードやテストからは参照されていない番号です。却下した案の理由や、この索引そのものの根拠を残すために載せています。

## モデルと図

### AD-1 extra_plots の返り値
- `extra_plots` は `(title, fig)` または `(title, fig, caption)` のリストを返す。新しい型は作らず、すでに使われていた 3 要素の形を、そのまま契約にした。
- 受け取る側は `title, fig, *rest` で展開すると決めた（caption = `rest[0] if rest else None`）。`title, fig = item` は、3 要素を返すモデルが 1 つ加わっただけで壊れるため使わない。
- 根拠: 3 要素を返すモデルが加わったとき、`title, fig = item` の形で取り出していたテストの補助関数が壊れた。
- 今の規約の場所: CLAUDE.md「アーキテクチャの規則」の「extra_plots の契約」、models/base.py。

### AD-2 決定境界の飾りにデータとサムネイルの区別を渡す
- `decorate_boundary_plot` に、キーワード専用の `ctx`（訓練・テストのデータと描画範囲）と `thumbnail`（既存の `ax` を渡されたとき True）を渡す。`thumbnail` が True のときは、インセットも凡例も描かず、注記は小さくするか省く。
- 根拠: k-NN が `plot_decision_boundary` を上書きし、直前の呼び出しの状態をインスタンスに残してサムネイルかどうかを見分けていた。この状態渡しは、呼び出しの順序に依存して壊れやすい。キーワード専用にしたのは、引数を受け取り忘れた上書きがテストではっきり失敗するようにするため。
- 今の規約の場所: CLAUDE.md「モデルプラグインの規則」10。

### AD-3 却下: plot_region_grid の見た目の上書き（参照なし）
- 補助関数 `plot_region_grid` に、カラーマップ・等高線・値の範囲の上書きと、速いレイアウトを足す案は採らなかった。
- 根拠: 別のパネルが必要なのは MLP だけで、意味も違う（ユニットごとの最小–最大の灰色、別の量の z=0 の等高線、確率ではないと明示したカラーバー）。確率用の補助関数を一般化すると、この区別がぼやける。速度は、8 パネル・1000 点で約 0.16 秒、余白を手動にしても約 0.13 秒で、API を変えるほどの差ではない。
- 今の状態: MLP は自前のレイアウトを持つ（models/mlp.py）。

### AD-4 学習時の警告の宣言
- モデルのクラス変数 `expected_fit_warnings`（(警告のカテゴリ, メッセージの正規表現) の並び）で、想定内の警告を宣言する。`BaseModel.fit` が、`warnings.catch_warnings()` の中でだけそれらを無視する。グローバルな警告フィルタは変えない。
- 使うのは、`fit` の中の警告を無視するだけのモデル。ロジスティック回帰は「収束」の判定のために警告そのものを記録するので、自前の局所的な `catch_warnings()` を使う。
- 根拠: 警告の抑制がモデルごとにばらばらの `catch_warnings()` で書かれていたのを、宣言に集めるため。
- 訂正: 当初は Gaussian にも「Variables are collinear」の警告の抑制を宣言する例を挙げていたが、撤回した。scikit-learn 1.9.1 にはこの警告が存在せず、QDA でクラスの共分散がランク落ちすると、警告ではなく `LinAlgError` になる（対応は AD-12）。
- 今の規約の場所: CLAUDE.md「モデルプラグインの規則」9。

### AD-4b 警告の見落としを防ぐテスト
- モデルの `build()` と `fit` を、`FutureWarning` と `DeprecationWarning` をエラーとして扱う設定の下で実行するテストを置く。
- 根拠: 探索の評価が `FutureWarning` などを黙って無視するため、scikit-learn の非推奨の引数を渡しても、テストが通ってしまう。
- 今の規約の場所: tests/model_checks.py。

### AD-7 色と記号の共通化
- 色の定数を `models/base.py` に置き、モデルと探索ページの図の両方が使う: 訓練（灰）、テスト（深紅、記号は ▲）、検証（ほぼ黒。CV は実線、OOB は点線）、最良（金の ★）、現在値・選択中の値（紫の縦の破線）。▲ はテストデータ専用にした。
- 探索手法は、どの図でも同じ色と記号にした: Grid は ■（`#4a3aa7`）、Random は ●（`#CC79A7`）、TPE は ◆（`#009E73`）。手法の色には、クラスの色（青・橙）を使わない。
- ヒートマップの背景は、彩度の低い単色系のまま。viridis は手法の色とぶつかるため採らなかった。
- 根拠: 手法の色とクラスの色が近く（Random の色と class 1 の橙）、TPE の記号 ▲ がテストの ▲ と衝突していた。
- 今の規約の場所: CLAUDE.md「アーキテクチャの規則」の「見た目の意味」、models/base.py、tuning/plots.py。

### AD-7a 色覚多様性の検証と配色の維持
- 手法の配色（AD-7）は、色覚多様性のシミュレーションの後も変えなかった。
- 根拠: 代わりに TPE の色を `#00745a` にする案を CIELAB の ΔE で比べた。2 型色覚（deutan）の Random と TPE の差は 18 から 24 に上がるが、3 型色覚（tritan）の Grid と TPE の差は 40 から 26、1 型色覚（protan）の Grid と TPE の差は 79 から 68 に下がる。全体として得がない。
- 決めたこと: 探索の図では、色がなくても手法が見分けられるようにする。手段は 4 つ（題の付いた別パネル、マーカーの形、手法ごとの線種と右端の手法名、目盛りラベル）。
- 今の規約の場所: tuning/plots.py と tests/test_tuning_plots.py。

### AD-7b 手法の文字色
- パネルの題・右端のラベル・目盛りラベルのように、文字だけに使う色として `METHOD_TEXT_COLORS` を置く。同じ色相のまま、白地とのコントラストを 4.5:1 以上にする。マーカーと線は AD-7 の色のまま。
- 最終の値: Grid `#4a3aa7`（コントラスト 8.56）、Random `#b64584`（5.03）、TPE `#007f5d`（5.01）。
- 訂正: 決める前の候補値（Random 約 `#9c4a80`、TPE 約 `#007a59`）は、この最終の値に置き換えた。小さな太字にも 0.5 の余裕を持たせるため、明度を下げて 5.0 前後にした。
- 今の規約の場所: tuning/plots.py（コントラスト ≥ 4.5、色相の差 ≤ 7° をテストで確かめている）。

### AD-7c 最良の星の縁の色

### AD-8 プレイグラウンドの指標の行
- 指標は 1 行に最大 4 列で並べ、値は短く（全角 10 文字程度まで）する。理由を伝えたいときは、値ではなくキャプションや説明文に書く（「いいえ (反復上限で打ち切り)」ではなく、「いいえ」とキャプション）。
- 根拠: ロジスティック回帰と MLP は指標が 6 列になり、長い値が切れて読めなくなった。
- 今の規約の場所: app_pages/playground.py。

### AD-9 テストで選んだ値の表示
- テストデータを使ってハイパーパラメータの値を強調したり選んだりする UI の要素には、UI では「（参考）」、図では "(reference only)" を付ける。強調には、なるべく CV や検証を使う。
- 根拠: 勾配ブースティングの「最良の木の数」と k-NN の k の曲線の ★ が、テストの正解率で選ばれていた。テストで選んだ値を、そのまま本来の選び方に見せてはいけない。
- 今の規約の場所: CLAUDE.md「アーキテクチャの規則」の「テストで選んだ値」。

### AD-12 想定内の学習失敗
- 想定内で、利用者が直せる学習の失敗は、専用の型 `FitError`（`ValueError` の派生）で表す。モデルは `raise FitError("<何が起きたか + 直し方>") from exc` と書く。プレイグラウンドは `model.fit` だけを囲み、`FitError` のときだけ `st.error` で表示して止まる。それ以外の例外は、実装のバグとして、そのまま表に出す。
- 根拠: スライダーで選べる 2160 通りの設定のうち 5 通りで、QDA の `reg_param=0` が `LinAlgError` になった。`ValueError` をまとめて捕まえると実装のバグが隠れるので、専用の型にした。探索の CV は `BaseModel.fit` を通らない（R1）ので、そこでの失敗は従来どおり NaN とエラー文になる。探索ページのサムネイルは `FitError` を捕まえ、その場所にメッセージを出す。
- 今の規約の場所: CLAUDE.md「モデルプラグインの規則」12、models/base.py。

### AD-13 プレイグラウンドの画像化のコスト（参照なし）
- プレイグラウンドの図を画像にするコストを測り、共有の契約は変えないと決めた。画像の解像度（dpi 200）と、余白を切り詰める指定（`bbox_inches="tight"`）は、Streamlit の `st.pyplot` の既定値をそのまま使う。
- 根拠: 1 モデル分の全図の書き出しは、dpi 200 / 150 / 120 で、MLP が 0.54 / 0.44 / 0.39 秒、勾配ブースティングが 0.33 / 0.29 / 0.26 秒、ほかは 0.30 秒以下（n=200、既定の設定）。dpi を 200 から 150 に下げて縮むのは 0.1 秒以下で、高解像度の画面では目に見えてぼやける。余白の切り詰めは MLP の層の図で約 0.14 秒かかるが、凡例を軸の外に置く図が多く、全体としては必要。低負荷なら MLP の既定でも約 1 秒で、基準の範囲内。
- 今の状態: app_pages/playground.py は、`st.pyplot` の既定値のまま図を出している（指定は置いていない）。時間の基準を超えたときだけ、測り直す。

### R1 CV は BaseModel.fit を通らない
- 探索は `make_estimator`（中で `build()` を呼ぶ）と `cross_validate` を直接使うので、CV では `BaseModel.fit` の上書きが効かない。そのため `build()` は単独で完結した推定器を返し、クランプやソルバーの選択などは推定器の中に書く。`fit` の上書きに許すのは、表示用の状態を足すことと警告を抑制することだけ。
- 根拠: 探索が `BaseModel.fit` を通らないので、`fit` の上書きに書いた処置は CV で効かない。k-NN の k のクランプ（訓練点が少ないとき、k が訓練点の数を超えると予測で失敗する）は、そのため推定器そのものの中に入れてある。
- 今の規約の場所: CLAUDE.md「アーキテクチャの規則」の「自己完結した推定器」、models/base.py の `make_estimator`。

## 探索ページと計測

### AD-5 整数パラメータのランダム抽出
- 整数の `ParamSpec.sample` は、線形なら各整数が等確率になるように抽出する。対数の整数は、optuna の `IntDistribution(log=True)` のランダム抽出と同じ離散化にする（下限は 1 以上）。
- 根拠: 以前の抽出は両端の整数が半分の確率でしか出なかった（degree 2〜5 で 0.165 / 0.332 / 0.338 / 0.165）。これでは Random と TPE の初めのランダムな試行の分布が違ってしまい、比較が公平にならない。乱数列は変わるが、同じシードなら同じ列になるので、再現性は保たれる。
- 今の規約の場所: tuning/space.py。

### AD-11 重いモデルの探索時間
- 探索ページの既定の実行が長くなりすぎないよう、次のように決めた。
  1. 既定の軸は `search_space()` の先頭の数値パラメータ 2 つ。モデル側で並びを教育的に決める（ランダムフォレストは max_depth と min_samples_leaf。木の数は予算のつまみなので、1 次元で見せる）。
  2. 任意のクラス変数 `tuning_defaults` は、探索ページの固定値の初期値だけを上書きする（ランダムフォレストの `{"n_estimators": 50}`）。プレイグラウンドと `build()` には影響しない。
  3. 手法ごとの試行回数の既定値を、コストの区分ごとに決める（low 25、medium 16、high 9。上限は変えない）。
  4. 推定時間が 30 秒を超えたら、実行の前に、短くする方法（試行回数を減らす、CV の分割数を減らす、全探索マップ（参考）を外す）を示す警告を出す。
- 推定の条件: 推定時間をエンジン分と描画分に分ける。実測と推定の比が [0.5, 2] に入ること（過小評価の方が悪い誤りなので、迷ったら多めに見積もる）。推定そのものが軽いこと（約 1.5 秒以下、かつ推定した実行時間の 10% 以下）。ライブ再描画の間隔は、直前の描画時間の 3 倍以上にして、描画が実行時間の約 25% 以下になるようにする。
- 目標と結果: 既定の設定で、ページ全体が 25 秒以下（マシンの負荷を併記し、3 回の最良で判断）。全 8 モデルで達成した。勾配ブースティングは、探索範囲の n_estimators を 10〜300 に狭めて 25 秒以下に収めた（狭める前は、負荷の下で約 27 秒）。
- 根拠: 変更前の実測（Moons、n=200、5-fold、3 手法）で、ランダムフォレストの軸が n_estimators と max_depth のとき、全探索マップ 14 秒 + 探索 52 秒。max_depth と min_samples_leaf にして n_estimators を 50 に固定すると、5 + 18 秒。時間の大半は直列の探索ループだった。
- 見送ったこと: 1 ラウンドの試行を並列に評価する案は採らなかった。TPE の ask/tell の順番と、累積学習時間の公平さの説明を単純に保つため。
- 今の規約の場所: CLAUDE.md「モデルプラグインの規則」11、tuning/budget.py、tuning/runner.py、app_pages/tuning.py。

### U1 30 秒警告の較正（AD-11）
- 既定の設定で「30 秒超」の警告が出すぎたので、しきい値の 30 秒は変えずに、推定を直した。エンジン側で、ランダムフォレストの推定が大きすぎないようにする。1 回の評価時間は、推定の予算の範囲で複数回測った中央値にする。推定はキャッシュして、同じ設定での再実行で揺れないようにする。表示は、10 秒未満は 0.5 秒刻み、10 秒以上は 5 秒単位。警告の判定は、丸める前の値で行う。
- 根拠: ランダムフォレストの推定が 29.2〜30.7 秒に対して実測 20.0 秒（比 0.65〜0.72）で、警告が 3 回中 2 回出た。しきい値を上げると、推定の多すぎを隠すことになる。ヒステリシスは、ページに状態を足すわりに、教材として説明しにくいので採らなかった。
- 結果: 既定の設定の 8 モデルを 3 回ずつ測って、30 秒超の警告は 0 回（0/24）。実測と推定の比はすべて [0.5, 2]（0.66〜1.06）で、過小評価はなかった。
- 訂正: 比が目安の 0.7 を下回ったのは、当初「6 回」と書いたが、丸める前の値では 7 回（ランダムフォレスト 0.662 / 0.690、SVM 0.669 / 0.695、MLP 0.673 / 0.697 / 0.673）。目安の範囲に入ったのは 24 回中 17 回。警告が 0 回で、比がすべて [0.5, 2] という判定は変わらない。
- 今の規約の場所: tuning/runner.py、app_pages/tuning.py。

### R-10 選択肢が変わるウィジェットの key
- 選択肢が、ほかのウィジェットの値によって変わるウィジェット（縦軸の選択肢が横軸で変わる、特徴量の選択肢がデータセットで変わる、など）は、key に「選択肢を決めている値」を含める。
- 根拠: `persist_state="session"` を付けると、選択肢が変わった後に、もう選べない値が復元されることがある。key に選択肢を含めておけば、選択肢が変わったときに別のウィジェットとして扱われ、無効な値は復元されない。
- 今の規約の場所: common/data.py、app_pages/tuning.py（CLAUDE.md「モデルプラグインの規則」3 の、安定した key と `persist_state` の規則の一部）。

### AD-14.1 データセットの登録
- `DatasetSpec`（名前、合成か実データか、説明、生成関数またはローダ、特徴量、元データの全クラス名、2 クラスの選び方、おすすめの特徴量の組、出典、ライセンス）と `FeatureSpec`（識別子、短い英語名、単位つきの英語の軸ラベル、UI の日本語名）で登録する。`DATASETS` の並びがメニューの並びで、Moons、Circles、Linear Separable、Palmer Penguins、Iris の順（第 2 段階で、末尾に Wine、Breast Cancer を足した。AD-14.11）。

### AD-14.2 DataConfig と normalized()
- `DataConfig` には、末尾に既定値つきで `features`（実データの 2 特徴量。None なら既定の組）と `standardize` を足した。位置引数での生成は、そのまま使える。

### AD-14.3 共通サイドバーと標準化のチェックボックス
- 実データでは、サンプル数とノイズのスライダーを描いたまま無効にし、「実データでは使いません（件数は固定）」と表示する（key と保持は安定したまま）。実データでは、特徴量の組を「おすすめの組」か、横軸と縦軸の個別の選択で選ぶ。
- 「特徴量を標準化する」のチェックボックスの既定は、実データでオン、合成データでオフ（文書にある Moons の数値が変わらないように）。
- 訂正: 当初は、チェックボックスの key を 1 つ（`data.standardize`）にしていたが、データの種類ごとに `data.real.standardize`（既定 True）と `data.synthetic.standardize`（既定 False）に分けた。key が 1 つだと、種類を切り替えたときに、利用者が変えた値が既定に上書きされるため。
- データの説明カードには、説明、件数、class 0・class 1 が元のどの種か、クラスの割合、同じ座標の点の数、出典とライセンスを出す。
- 今の規約の場所: common/data.py。

### AD-14.4 標準化はモデル側
- 標準化は、特徴量のスケールで結果が変わるモデル（`scale_sensitive = True`、k-NN と SVM だけ）に、モデル側で付ける。推定器は `make_estimator(model, params, standardize)` だけで組むと決めた。`BaseModel.fit` と探索エンジンの両方がこれを使う、唯一の経路。`StandardScaler` を前段に付けた Pipeline ごと交差検証するので、スケーラは各 fold の訓練側だけで学習され、検証データの情報は漏れない。
- 図は、標準化していない元の単位（mm、g、cm）のまま描く。決定境界は Pipeline を通して計算する。
- ロジスティック回帰と MLP は、モデルの中ですでに標準化している。木ベース（決定木・ランダムフォレスト・勾配ブースティング）と Gaussian の 3 種類は、標準化を付けない（`scale_sensitive = False` のまま）。特徴量ごとの単位（スケール）の影響は、次のとおり。
  - 木ベース（決定木・ランダムフォレスト・勾配ブースティング）と LDA: 特徴量ごとの拡大縮小で、結果が変わらない（違いは数値の誤差の範囲）。木ベースは、分割のしきい値が単調変換でほぼ同じ分け方になるため。ランダムフォレストと勾配ブースティングは、Penguins（くちばしの長さ × 体重）のシード 42 で、5 通りの倍率とも予測が 100% 一致した（実測）。ただし、シード 0〜19 と 42 の計 21 シードでくちばしの単位を変えると、決定木は 2、RF は 2〜4、GB は 4 シードで、テスト 66 点中 1〜数点の予測が変わった（測定。決定木は原因を確かめた: 木の構造は元の単位でも同じで、違った 1 点はしきい値から約 4e-7 の距離にあり、float32 の丸めの範囲だった。RF と GB は個別には確かめておらず、同じ丸め誤差と見ているが、未確認）。「スケールに左右されない」と言えるのは、この 2 系統だけ。
  - Naive Bayes: 予測クラスも、単位で変わりうる。原因は `var_smoothing`（全特徴量の最大分散に 1e-9 を掛けた値を分散に足す）で、影響は分散の比（標準偏差の比の 2 乗）に比例する。Penguins の「くちばしの長さ × 体重」（体重とくちばしの長さの標準偏差の比は約 80。2 クラスの 219 点で 79.7）で、片方の単位だけを変えたときの、テスト点での確率の最大の動き（シード 0〜19 と 42 の計 21 シード）は、体重を ×10 にすると約 1.7e-3、体重を ×100 にすると約 0.16（予測クラスも変わる）、くちばしの長さを ×0.0025 にすると約 0.71（予測クラスも変わる）だった。体重を ×0.0025 にしても、約 1.7e-5 と小さい。
  - QDA（`reg_param = 0`）: 限界は、標準偏差の比ではなく、絶対値で決まる。クラス内の共分散の固有値が約 1e-4 以下になると `LinAlgError` になる（アプリでは `FitError`、AD-12）。Penguins の「くちばしの長さ × くちばしの高さ」で高さの単位だけを変えると、×0.02 まで 20 シードすべてが通り、×0.01 以下（mm から m を含む）では 20 シードすべてが失敗した。`reg_param > 0` の QDA は、元の単位で単位行列に向けて縮めるので、不変ではない（`reg_param` の説明に、単位への依存を書いた）。
  - Naive Bayes と QDA を `scale_sensitive` にして標準化を付ける案は、今の設計では採っていない。今後の設計の課題として残している。
  - 標準化のノートの判定（`app_pages/playground.py` の `standardize_note`）は、クラス名と Gaussian の variant の文字列に頼っている。モデルが増えたら、`BaseModel` の属性かメソッドにする（今後の課題）。それまでは、`scale_sensitive = False` の全モデルの分類を確かめる smoke のテスト（`test_every_non_scale_sensitive_model_is_classified`）が、未分類の追加を検出する。
- UI の言い方の方針: 木ベース（決定木・RF・GB）と LDA は「特徴量ごとの拡大縮小で、数値の丸めによる違いを除いて結果が変わりません」（木ベースは実測で、ごくまれに数点変わるため、「結果をほとんど変えません」と言う）、ロジスティック回帰と MLP は「モデルの中ですでに標準化しています」、Naive Bayes と QDA は「単位によって結果が変わることがあります。このモデルには標準化を適用していません」と言う。
- 訂正: 以前の「現実的な単位の範囲で、Naive Bayes・LDA・QDA（`reg_param = 0`）もスケールに左右されない」「極端な比（約 1e5 以上）で崩れる」は、言い過ぎだったので訂正した。約 1e5 は、崩れ始める下限ではなく、ほぼ完全に崩れる目安だった。さらに前の「Naive Bayes の差は約 1e-5」も、シード 0 だけの実測で、過小評価だった。
- 今の規約の場所: CLAUDE.md「データセットの規則」6、models/base.py の `make_estimator`。

### AD-14.5 図の契約
- 図の軸ラベルは、実データでは単位つきの名前にする（`PlotContext` の `feature_labels`）。`PlotContext` の `feature_names` は短い英語名、`class_names` は選んだ 2 クラスの名前。UI の文の中のクラス名は「class 0 / class 1」のままで、対応はデータの説明カードが示す。
- `Bounds.from_data` の余白は、絶対値の 0.5 から、軸ごとの「範囲 × `pad_frac`（0.08）」に変えた。単位で桁が違う実データでも、図が潰れないようにするため。探索ページの fold の図も同じものを使う。
- 探索ページのヒートマップの色の範囲は、下端を有限値の 5 パーセンタイルにし（従来の 0.5 の床は外す）、平らなマップ（Iris）でも一色にならないよう、幅を最低 0.05 にする。
- 経緯: 呼び出しの移行のあいだ、`pad`（絶対値の余白）を残す互換の引数を一時的に置いたが、移行が済んで撤去した。
- 今の規約の場所: models/base.py、tuning/plots.py。

### AD-14.6 Iris の重複点
- Iris の重複した点には、ジッタを入れない（データを変えてしまい、再現性も損なうため）。代わりに、k-NN の説明と k の曲線の題を条件つきにした。距離の重みを使うと訓練の正解率は 1 になるが、同じ座標にラベルの違う点があるときは、どの k でも 1 に届かない。そういう点があるときは、k の曲線の題とキャプションで、その点の数と、訓練の正解率が 1 に届かないことを示す。
- 今の規約の場所: models/knn.py。

### AD-14.7 実データのテストと時間の予算
- プレイグラウンドの通しテスト（smoke）の時間は、1 テスト 15 秒以下を主軸にし、ファイル全体は、負荷 3 以下で 120 秒以下を目安にする（合否の条件にはしない）。ハングを検出する上限（20 秒 / 45 秒）は変えない。
- データセットの登録の契約テストは、AppTest を使わず 1 秒未満で流す（全データの `load()` の形、ラベル、決定性、CSV の SHA-256、ネットワークを使わないこと）。実データの AppTest の追加は 3 本までにとどめ、全モデル × 全データセットの AppTest は流さない。各モデルのテストには、実データの `DataConfig` のケースを 1 つずつ足す。
- 今の規約の場所: tests/test_datasets.py、tests/test_app_smoke.py。

### AD-14.8 多クラスへの備え（参照なし）
- ここまでの決定は、どれも多クラスへの拡張を妨げない: 登録情報は元データの全クラス名を持ち、`DataConfig` にはあとから `classes` を足せ、`make_estimator` とエンジンは、スコアの計算と標準誤差を除いて、クラス数に依存しない。
- 残っている 2 値の前提（`PROBA_CMAP`、`predict_proba[:, 1]`、2 色の `CLASS_COLORS`、`roc_auc`、Hanley–McNeil の標準誤差、各モデルの図）は、将来の多クラスの課題の設計の範囲にした。その課題は、「K クラスの確率を 1 枚の絵で見せる方法」の検討から始める。
- 今の状態: data/specs.py が元データの全クラス名を持つ。

### AD-14.9 data/ の構成と補助
- 公開 API（`DataConfig`、`DATASETS`、`generate`、`DatasetSpec`、`FeatureSpec`、`class_balance`、`is_imbalanced`）は、`data.generator` から import できるままにする。中身は `specs.py`、`synthetic.py`、`real_datasets.py`（`data/real/` ディレクトリと紛らわしくないよう、`real.py` にはしなかった）に分けてよい。`data/` は streamlit・`models`・`tuning` を import しない（探索のワーカーからも読まれる純粋なコードにするため）。CSV の場所は、実行時のカレントディレクトリではなく、ファイルの位置からの相対で決める。
- `DatasetSpec` の補助として、`is_real`、`feature_keys`、`feature(key)`、`binary_class_names`、`default_features`（`presets[0]`、なければ先頭の 2 特徴量）を置く。どれも、値の唯一の元。
- 重なった点の数は `duplicate_stats(X, y)` が数える。`shared` は座標が 2 回以上出てくる点、`hidden` は同じ座標にほかの点があって見えない点、`conflicting` はラベルが 2 つ以上ある座標の点で、誤りの数ではない。データの説明カードと k-NN の文言（AD-14.6）が、この 1 つの定義を使う。実測では、Iris の花弁が 35 / 20 / 3、がく片が 39 / 22 / 24、Penguins の既定が 4 / 2 / 0（shared / hidden / conflicting）。
- 今の規約の場所: data/generator.py、data/specs.py、data/real_datasets.py。

### AD-14.10 図の中のクラスの呼び方
- 図の中でクラスを指すときは、先に「class k」と書き、実データでは種名を括弧で添える（"class 0 (Adelie)"、"class 1 (Chinstrap)"）。合成データは "class 0" / "class 1" のまま。UI の文とカラーバー（`P(class 1)`）も class 0 / class 1 のまま（対応はデータの説明カード）。`PlotContext.class_labels` が、この呼び方を返す。
- 根拠: Gaussian の密度図の凡例が "p(x | Adelie)" で、同じ画面の境界図のカラーバーが "P(class 1)" だと、同じクラスの呼び方が 2 つ並んでしまう。「class 1」という語を、UI の文・カラーバー・凡例のすべてに共通させて、学習者が結びつけられるようにした。種名を図から消す案は、教材として分かりにくくなるので採らず、確率の軸を種名にする案は、`draw_background` の契約が変わって波及が大きいので採らなかった。
- 範囲の明確化: ロジスティック回帰の係数の図の横軸の説明は、カラーバーと同じ「軸や式の側の表記」なので、class 番号のままにする。
- 今の規約の場所: CLAUDE.md「UI と図の決まり」、models/base.py の `PlotContext.class_labels`。

### AD-14.11 第 2 段階の実データ（Wine と Breast Cancer）
- 決めたこと: scikit-learn 同梱の Wine と Breast Cancer（Wisconsin Diagnostic）を、`DATASETS` の末尾に足した（`data/generator.py` の変更は、docstring の 1 行、import、`DATASETS` の並びの 3 か所だけ。`DataConfig` のフィールドや関数の契約は変えていない）。どちらも `load_*` から読み、`fetch_*` や HTTP は使わない。
- Wine: 元の 3 クラスのうち、品種 2 と品種 3 を使う（`binary_classes = (1, 2)`。class 0 = 品種 2、class 1 = 品種 3）。品種 1 を含む組は分けやすすぎて、演習にならないため（品種 1 と 3 の組では、2 特徴量の 78 組のうち 12 組で、標準化ありの LR の 5 分割 CV（シャッフルあり、シード 0）の正解率が 1.000 になった。品種 1 と 2 の組は 0 組、品種 2 と 3 の組は 0 組。中央値は順に 0.812、0.865、品種 1 と 3 が 0.953。独立の再現）。クラス名は元データに固有名がないので "cultivar 1〜3" とし、固有名は書かない。少数派の割合は約 0.403 で、`is_imbalanced` の閾値 0.4 のすぐ上（False）。判定は訓練とテストを合わせた y で行うので、シードや分割で揺れない。
- Breast Cancer: class 1（橙）= 悪性、class 0（青）= 良性（`binary_classes = (1, 0)`）。scikit-learn の target（0 = 悪性）と向きが逆になるのは、「探したい方 = 少数派 = class 1」の習慣にそろえるためで、少数派の割合は約 0.373（`is_imbalanced` が True）。向きの取り違えが最大の危険なので、`DataConfig.load` の結果と scikit-learn の target を、点ごとに突き合わせるテストで守る。`DataConfig.load` の実装は `(c0, c1)` の大小に依存しない。
- 特徴量は、元の列から教育に使うものだけを登録する（Wine は 13 列から 6 つ、Breast Cancer は 30 列から 8 つ）。ローダは、登録した列だけを、列名で引いて登録順に返す（列の番号は直書きしない）。key はほかのデータと同じ、英小文字とアンダースコアの識別子にそろえ、元の列名に空白があるときはローダで写す。単位は、出典に明記がないので付けない（推測で単位を書かない）。
- 説明: Breast Cancer の説明には、「診断に使うものではない」「悪性を見逃す誤りと、良性を悪性と誤る誤りは、正解率だけでは区別できない」を書く（アプリの指標は正解率が中心のため）。標準化についての新しい主張は、この段階では足していない。
- 出典とライセンス: UCI の 2 つのページ（DOI 10.24432/C5PC7J と 10.24432/C5DW2B）を出典とし、ライセンスは "CC BY 4.0 (UCI version; terms for the scikit-learn copy not stated)"（Iris と同じ書き方）。scikit-learn の Wine の説明にある作者名は、UCI と食い違っている（Iris の説明の写し間違いと見ている。未確認）ので、出典には UCI 側を使う。
- 影響: `DataConfig.normalized()` は spec の名前ごとに分かれるので、キャッシュのキーと探索結果の同一性は、既存のデータと衝突しない。`tests/scale/test_scale_models.py` は `DATASETS` を列挙するので、件数が 78 × 5 から 78 × 7 に増える。
- 残っている確認: Wine の 2 クラスは訓練が約 83 点と少ない。探索ページの CV の fold あたりの点数と予算が妥当かは、Tuning の確認事項（未確認）。
- 残っている確認: Breast Cancer の登録した 8 特徴量の 28 組のうち 4 組（mean_concave_points × worst_concave_points、mean_smoothness × mean_concave_points、mean_smoothness × worst_concave_points、mean_smoothness × worst_smoothness）は、QDA（`reg_param = 0`）が、単位を変えなくても `FitError` になる（クラス内の共分散の固有値が約 1e-4 以下。AD-14.4 のとおりで、設計どおりの案内）。Wine の 15 組は、すべて通る。`models/gaussian.py` の案内の文言（「ノイズを増やしてください」）は、実データにノイズの設定がなく、原因の言い方も実データに合わない。これは Models 側の別件で、この項目では直さない。
- 今の規約の場所: data/real_datasets.py（spec とローダ）、data/generator.py（登録）、tests/test_real_datasets.py、tests/test_datasets.py。CLAUDE.md「データセットの規則」の追記は別の単位で行う。

## テストの運用

### AD-6 テストで Agg バックエンドを固定する
- `tests/conftest.py` の先頭で、matplotlib のバックエンドを Agg に固定する（pyplot を import する前に）。
- 根拠: AppTest はスクリプトを別のスレッドで実行するので、GUI のバックエンド（TkAgg など）が選ばれると、テストの収集順によっては、プロセスごと落ちる。
- 今の規約の場所: tests/conftest.py、CLAUDE.md「テスト」。

### AD-15 性能目標のテスト（timing）
- 「ハングを検出する緩い時間の上限」（秒の単位。既定の実行に残す）と、「性能目標の確認」（推定の比が [0.5, 2] に入る、対話の予算に収まる、など）を区別する。後者には `@pytest.mark.timing` を付け、`addopts` で既定の実行から外す。ゲートでは、`uv run pytest -m timing` を 3 回流し、負荷を併記し、テストごとに最良の結果で判定する。
- 根拠: 実測の時間の assert は、マシンの負荷で結果が揺れる。既定の実行に置くと、テストが通ったり落ちたりする。性能目標のテストに「忙しいときは skip」を使うことも、黙ってテストが消えるので採らない。
- 今の規約の場所: CLAUDE.md「テスト」、pyproject.toml の `markers` と `addopts`。

### AD-16 メモリ枯渇の再発防止
- 次の 5 つを決めた。
  1. 探索エンジンの並列数の上限を決める関数は 1 つだけ（`max_jobs()` = `min(4, max(1, CPU 数 // 2))`）。環境変数 `ML_PLAYGROUND_MAX_JOBS` があれば、それを優先する（1 なら直列）。
  2. 並列ワーカーの待機時間（`WORKER_IDLE_TIMEOUT`）は 60 秒。
  3. テストでは `ML_PLAYGROUND_MAX_JOBS=1` を既定にし、セッションの終わりにワーカーを片付ける。並列の経路そのものを確かめるテストだけが、`n_jobs` を明示する。片付けは joblib の内部の属性に頼るので、その属性が今の joblib に存在することを確かめる小さなテストを置く。
  4. n=1000 を使うテストは timing マーカーに移し、既定の実行のテストは n ≤ 300 を目安にする。
  5. 全体テストは、排他制御つきの実行スクリプトで、担当者が 1 人でまとめて流す。ほかの人は、自分のテストファイルだけを流す。
- 根拠: テストが 7 本同時に走り、Python のプロセスが約 110 個、メモリ 14/15 GB、スワップ 3.7/4 GB になって、マシンが止まりかけた。探索の並列数が CPU 数（16）だったので、7 本 × 16 ワーカーになっていた。待機時間を 60 秒にしたのは、4 並列のワーカーが待機中も約 0.8 GB を持ち続け、再利用で節約できるのは起動の 2〜3 秒だけ（探索 1 回の 5〜25 秒に比べて小さい）ため。
- 今の規約の場所: CLAUDE.md「テスト」と「コマンド」、tuning/evaluate.py、tests/conftest.py。

### AD-17 大規模検証のテスト（scale）
- `tests/scale/` に、大きな条件（n=1000、複数のシード）で正しく動くかを確かめるテストを置く。各ファイルに `pytestmark = pytest.mark.scale` を付け、`addopts` で既定の実行から外す。timing とは別で、性能目標の assert は置かない（置くなら timing を併用する）。置くのは、ハングを検出する緩い上限だけ。
- 流し方: 運用では、テスト品質の担当者が予約枠で流す。並列数は `ML_PLAYGROUND_MAX_JOBS=1` のまま（AD-16 のメモリの前提）。
- 落とし穴: `-m scale` を付けずに流すと、全件が deselect されて 0 件になり、終了コード 5 になる。そのため「通った」ように見えてしまう。
- 今の規約の場所: CLAUDE.md「テスト」、pyproject.toml。

### AD-19 探索の CV の非推奨の警告の見張り
- 決めたこと: 探索の CV が scikit-learn の非推奨（FutureWarning・DeprecationWarning）を出さないことを、テストで恒常的に見張る。`tuning/evaluate.py` の `evaluate()` は、想定内の警告を抑制する。そのため、非推奨の警告も一緒に隠れうる。テストは `evaluate()` を通さず、`make_estimator` + `cross_validate` を直接呼んで、この 2 種類の警告をエラーにする。`MODEL_REGISTRY` の全モデルで parametrize するので、新しいモデルは登録すれば自動で対象になる。警告を出す推定器でテストが失敗することを確かめる負の対照も置く。
- 根拠: `evaluate()` が想定内の警告を抑制するので、scikit-learn の非推奨の警告は、探索の CV からは見えない。プレイグラウンドの `fit` は警告を局所的にしか抑制しないので、そちらでは見える。非推奨のまま放置すると、次の版で削除されたときに初めて壊れる（例: `LogisticRegression` の `penalty` は非推奨で、`CLAUDE.md` の落とし穴に残っている）。削除された引数は、警告ではなく `TypeError` になり、探索の CV では NaN とエラー文として現れる。この見張りが防ぐのは、削除の前の、警告の段階での見落としである。
- 条件: 対象は FutureWarning と DeprecationWarning だけで、ConvergenceWarning は想定内として別に扱う（モデルの `expected_fit_warnings`）。データは小さく、シードを固定する。既定の実行に残す（時間はハング検出の緩い上限だけ）。依存（scikit-learn など）を更新するときは、このテストを最初に流す。
- 現状: このテストは、足した時点で現行のコードで通り、コードの修正は要らなかった。
- 今の規約の場所: tests/test_tuning_engine.py、CLAUDE.md「テスト」。
